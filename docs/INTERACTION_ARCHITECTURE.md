# Web interaction engine v2

The web controller calls `EngineSession.step()`. Within one five-day world round the engine commits up to four
character batches. A committed question creates an item for one present recipient. The answer is committed before
the asker is scheduled again. A batch never reads output generated by a parallel call in that same batch.

`engine_ledger`, `engine_items` and `engine_turns` store the state and recorded model output. Items include source,
responsible character, topic, creation order, supply and response history, wait condition and closure reason.
States are open, seen, waiting, resolved and obsolete. Items omitted by the scheduler cap carry forward.
Repeated invalid metadata backs off. Waiting for a person outside the cast is refused with feedback.

The model chooses `interaction.addressed`, `interaction.requests`, `interaction.wait_for` and any substantive
action. The engine checks that an addressee is present and that a referenced item belongs to the actor.
The Harness alone commits world facts, retaining baseline's permissive executor and the two Harness modes' gates.
Remote messages remain unavailable until their arrival day and PREPARE delivery.

Selection identity is `round + epoch + interaction step`. Proposal batches continue to enforce their current
version and epoch. The ledger is rederived from committed batches, dialogue and stored model output in control
order. Commit and ledger materialization share a transaction. Audit replay parses recorded output without calling
the model. Branches inherit the ledger at the chosen round start. `engine.v2` refuses to resume v1 sessions.

The audit summary includes interaction steps by round, item coverage, waiting, invalid and repeated actions,
unresolved items and stop reason. A total budget stop does not create a world terminal.
Web users can explicitly add 50 calls and up to US$0.25 to a suspended session. The extension is keyed by the
request id, logged, and applied before resume. Existing frozen results remain untouched.

## Human D/P validation

1. Start a **new** D/P web session under the new engine version with the live server gate configured by a human.
2. In the player view, ask Shi a question that requires Liu's advice. Confirm that the timeline shows Shi's
   question, Liu's answer and Shi's next decision in ordered steps of one world round.
3. Send a remote letter and confirm the recipient's view stays unchanged until PREPARE on its arrival day.
4. Observe one rejected action. Verify its feedback remains in the actor's next context even if several rounds pass.
5. Check the player pause before consequential actions, run budget and unresolved-item audit, and a restart from
   a suspended session. Use D/P configurations only; do not overwrite `runs/freeze.json` or old run directories.

Offline mock tests verify mechanics and replay. They do not establish how reliably a paid model negotiates.
